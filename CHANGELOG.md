# am-lang-core changelog

The runtime and standard library every AmLang program links. Core is released
with the compiler and carries the same version; changes that need a compiler
change are also in the compiler's `docs/releases/CHANGELOG.md`. Redmine numbers
are issues in the private tracker.

## [0.16.0] - Unreleased

Changes since 0.15.0. Needs amlc 0.16.0.

- **StringBuilder appends a string with one copy** (2026-11-20, Redmine #466). Its buffer was a `List<UByte>` filled one checked `add` per byte (`List<UByte>.add` alone was 4% of a v2 self-build). - **`a + b` on strings no longer re-reads `a`, and `indexOfAfter` is native** (2026-11-20, Redmine #466). Every String carries its hash and character count, computed when it is built, and `+` computed both again over all of `a` and `b`: a loop of `s = s + piece` spent most of its time hashing, not copying (82% of the v2 compiler's self-build). `+` now continues from the left operand's hash (the FNV-1a state is recovered by inverting the final avalanche, which is a bijection) and adds the two character counts, walking only `b`'s bytes; it recounts the join in the one case the counts don't add up (a `b` that starts with a UTF-8 continuation byte, which can complete a sequence `a` ends with), and a NUL in `a` keeps `a`'s hash as before. Results are bit-for-bit those of hashing the joined bytes. The character count of any new string also skips the UTF-8 decoder for ASCII bytes. `indexOfAfter(s, start)` was AmLang comparing two checked `characterAt()` calls per step; it is now C: `memchr`/`memcmp` when both strings are ASCII, a UTF-16 unit comparison otherwise (same results, surrogate halves included, and a NUL in the text no longer matters). It is now `#noThrow`. Together with v2's StartupGenerator and extern-scan fixes (same issue), v2 builds itself in 36 s instead of 170 s (v2 at -O0, gcc stubbed) and am-lang-core in 2.0 s instead of 6.6 s. New `tests/StringConcatSearchTests.aml` (10 tests: hashes and lengths of joins against a fresh `fromBytes` of the same bytes, empty operands, non-ASCII, a sequence split across the seam, a NUL in the left operand, a 2,000-round loop-built string as a `HashMap` key, `indexOfAfter` on ASCII, out-of-range arguments, non-ASCII and astral text, and past a NUL). 555/555 under v1 and v2.

- **AmigaOS and MorphOS: a thread that doesn't stop during an out-of-memory shutdown is removed after 10 s instead of being left running in the unloaded program** (2026-11-19, #446). Since #446 main waited `AMLC_OOM_JOIN_TIMEOUT_MS` for the other threads and then exited without the ones that never reached a stop point (a loop with no `receive`, `join`, `sleep` or `new`, or a thread stuck in an OS call). Now the timeout there is 10000 ms (3000 elsewhere, unchanged), measured with `DateStamp` (a busy worker at main's priority stretches each one-tick poll to its whole quantum, so counting `Delay(1)`s ran long), and then `__amlc_remove_stuck_workers` (`core.c`) handles each worker that is neither `done` nor already removed: under `Forbid`, it finds the task in `TaskReady`/`TaskWait` by `tc_UserData == iso` (under `Disable` for the walk), checks `done` again, empties its `tc_MemEntry` and calls `RemTask`, then closes and unbinds its mailbox so no `Signal` goes to it, and prints `Thread 'busy' did not stop within 10 s; removed` (or `...; its task has gone` if it is in neither list). New `aisolate.removed`. What the task owned is leaked, never freed from main: its Process structure and stack (a DOS packet it had in flight may still be replied into them), its current-directory lock, and its isolate (heap, statics, mailbox, queued messages; the task's own handle is never dropped, so nothing frees the `aisolate`), and so its open files (still locked) and libraries. A join on it gives up as before; exit status stays 20. AROS (pthread-based `Thread.c`) is unchanged: pthread.library keeps its own bookkeeping of the task. Tests: `examples/OomShutdown/run.sh --amiga` now runs `busy` under amiberry (exit 20 with the message, about 11 s of emulated time for the whole run; then the program again, `Avail`, `Dir` and `Wait 30` in the same shell, all RC 0, no guru), the other twelve modes and the file checks still pass on AmigaOS, linux-x64 (and its ASan builds) passes as before, and a new `morphos-ppc-docker` target in the example builds and links for MorphOS (not run).
- **Breaking: out of memory shuts the program down instead of throwing `OutOfMemoryException`** (2026-11-18, #446). ### Fixed

- **`HashSet.remove` frees its slot and releases the value, and a resize no longer brings removed values back** (2026-11-21, Redmine #500). `currentValueIndex` never went down, so a removed value stayed referenced in `values[]` (a leak, and a set under add/remove churn grew without bound), and the rehash in `add()` re-inserted every slot from 0 to `currentValueIndex`, removed ones included: after enough adds to trigger a resize, `contains(removed)` was true again and `size` was wrong. `HashSet` now has the structure `HashMap` already had: `remove()` pushes the slot on a free list (`freeHead`, linked through `nextIndexes`) and sets its value to `default(T)`, `add()` takes a free slot before extending, the rehash walks the old bucket chains so only live values move, and growth is triggered by the live `size` alone (the old `currentIndex` counter is gone). `HashMap`'s own remove path was checked with the same add/remove/add-past-resize sequences and was already correct. The public API is unchanged; iteration order within a bucket may differ after a resize (it was unspecified). New HashSetRemoveTests: add/remove/re-add, removal from the head, middle and tail of a chain, removed values stay gone across two resizes, size and `contains` after every step over 3000 adds, `clear` then reuse, removed objects released (`instances()` back to 0, set and map), and 100000 add/remove cycles on a set and a map (a fraction of a second). Four of the nine fail with the old HashSet. 687/687 under v1 and v2.

- **`HashMap.clear()` and `HashSet.clear()` release what they held** (2026-11-21, Redmine #396). They reset the bucket indexes only, so every key and value stayed referenced by the backing arrays until its slot was reused: a cleared map of objects kept them all alive. They clear the used slots now (`Array.clearRange`), as `List.clear()` does. Tests: tests-v1-only ListOfAnyArcV1Tests.clearReleasesObjects (`HashSet<Any>` and `HashMap<String, LaArcThing>`, instances() back to 0).
- **AmigaOS/MorphOS: `Thread.join()` and main's out-of-memory shutdown wait until the worker task has left the program's code** (2026-11-21, Redmine #459). Both waits return when they see `iso->done`. That flag was set in `__amlc_isolate_teardown`, before the worker's `Am_Threading_Thread__InitTask` (amigaos and morphos-ppc `Thread.c`) had dropped its own handle and returned to dos.library. So main could exit and unload the program's segments while the worker was still running a few instructions of that code. On the Amiga family, `done` is now set by `__amlc_isolate_task_exit` (core.c), the task's last call. It drops the task's handle, lowers the isolate count, clears `tc_UserData` and sets `done`, all under a `Forbid()` that is never `Permit()`ed: the entry returns to dos.library, and Exec's removal of the task ends the Forbid. Nothing in that section may `Wait()`, so it calls no `free()` (libnix's malloc takes a semaphore). When the task held the last handle (a thread whose `Thread` object was already dropped), the isolate stays in the live list, done and without handles, and the next `Thread.start` frees it (`__amlc_reap_isolates`). #446's RemTask path and the 10 s timeout are unchanged: a removed task is never `done`. The libc (pthread) path is unchanged. Its first joiner waits in `pthread_join`, and a POSIX process exit doesn't unmap code under a running thread. New example `examples/ThreadExitRace` (`./run.sh --amiga`) was run on AmigaOS 3.1 under amiberry: 20 runs of 10 rounds of 12 joined threads, 20 runs of 16 joined threads and then an immediate exit, 3 runs of 80 threads with dropped handles (free memory stays flat), and 10 runs of nested joins, all in one session, then Avail, Dir and one more run. All 54 runs exited 0 with no guru, and no worker task was still bound to its isolate after a join. OomShutdown `--amiga` passed all 13 modes, including busy (removed after about 11 s). MorphOS builds of both examples link. linux-x64: core 625/625 under v1 and v2, tests-v1-only 18/18, am-tests 11/11, OomShutdown with ASan.
- **AmigaOS/MorphOS: a program no longer leaks a signal bit of the Shell it runs in, so `Thread.receive()` on main keeps working after about 15 runs** (2026-11-21, found while testing Redmine #459). Main's mailbox takes a signal bit from the main task in `__amlc_isolate_boot_main` (`AllocSignal`, core.c), and only a worker's teardown gave its bit back. Main is the Shell's own process, so every run lost one bit of that Shell for good; after about 15 runs `AllocSignal` failed, main's mailbox had no signal, and main's first `Thread.receive()` threw "Thread.receive: the mailbox is closed" at once. Shown on AmigaOS 3.1 under amiberry: with the old core, runs 17 to 20 of 20 failed that way. An `atexit` handler now frees the bit. It touches no malloc'd memory, which libnix may already have released. After the change, all 20 runs passed under amiberry, and the linux-x64 suites were unchanged.
- **`a is Color` and `a as Color` on an `Any` that holds an enum** (2026-11-21, Redmine #392). The flags of a `nullable_value` carry the enum's tag in their high byte (`nullable_value.flags` is 16 bits), and `__any_is_enum(a, tag)` (core_inline_functions.h) tests it. `__set_primitive_null` and `__set_primitive_nullable` kept the flags in an `unsigned char`, which would have cleared the tag; they use `unsigned short` now. The compiler change is in the compiler's changelog. Test: AnyEnumIsAsTests (14).
- **`TaskScheduler.handleMainTasks()` and the task runners survive a failed worker's notice without losing messages** (2026-11-21, Redmine #467). With the failure notices added for #467, `handleMainTasks()` let the `ThreadFailedException` out of its drain before putting back the non-Task messages it had already taken, so those were lost; it now stops at the notice, re-sends what it took (in order) and then throws, once. A `TaskRunner` worker is the parent of any thread its tasks start, so such a thread's death ended the runner's receive loop and left every later task and `runAsync` caller of that thread type waiting; the runner now logs the notice and keeps serving, as it does for a task that throws. New RunAsyncTests: `handleMainTasksKeepsMessagesWhenAWorkerFailed` (two messages before the notice and one after all arrive, the exception is seen once) and `aTaskRunnerOutlivesAThreadItsTaskStarted` (a `runAsync` queued behind the notice still completes); both failed before the fix (the dead runner also failed `twoRunsInFlightEachGetTheirOwnResult`). 580/580 under v1 and v2.
- **A send that fails on a nested child that isn't sendable no longer leaves partial copies behind** (2026-11-21, found with #467). `__amlc_copy_object` returned NULL when a child could not be copied without releasing the object it had already allocated for the parent, and `__amlc_message_create` only releases a non-NULL root, so sending `Holder(new Mutex())` left a copy of `Holder` alive (one per failed send) until the thread ended. The partial object is released where the copy fails. New `ThreadTests.testFailedNestedSendLeavesNoPartialCopy` (`instances(...)` before and after). 578/578 under v1 and v2.

- **`String.lastIndexOf` is one backwards scan: linear, sees past a NUL, counts in the same units as `indexOf`** (2026-11-20, Redmine #469). `Am_Lang_String_lastIndexOf_0` called `strstr` again from every match onwards: quadratic when matches overlap and are long (`"aaa...a"` with a needle of half its length), and blind to anything after a NUL. It now scans from the last possible start with `memcmp` for ASCII strings, and compares UTF-16 units (as `indexOfAfter` does, #466) otherwise, so surrogate halves match and the result is a unit index. - **String templates keep a part that contains a NUL, and join in one pass** (2026-11-20, Redmine #468). `__concatenate_strings` (`core.c`, used by v1 for `"[$a|$b]"`) joined the parts with `strcat`: a part holding a NUL was cut there while `length` was still the sum of the full byte lengths, so the result ended in uninitialised bytes, and `strcat` rescanned the result for every part (quadratic in the number of parts). It now `memcpy`s each part at a running offset by its byte length, NUL-terminates, and takes hash and unit count from `__string_hash_and_units` as before, so the result equals the same string built with `fromBytes` (hash, length, bytes). - **A TRACKOBJECTS/DEBUG build removes an object from the allocation registry in O(1), not by scanning all 51200 slots** (2026-11-20, trackobjects). `amlc test` builds define `TRACKOBJECTS`, and every deallocation looped over `allocations[MAX_ALLOCATIONS]` to clear the object, so a test binary with millions of allocations ran at about 12K allocations/s (v2's suite took 22m55s). The object now stores its registry slot (`class_object_properties.registry_slot`, 1 + index, 0 = not registered; only under `DEBUG`/`TRACKOBJECTS`), and `__amlc_unregister_object` clears that slot after checking it still holds the object; objects never registered (registry full) are not scanned for. The shutdown dump (`Allocated objects N`, `Object still alive`) is unchanged. v2's suite: 22m55s to 19s (103/103 both); core suite output tail identical.
- **What frames skipped by an out-of-memory jump held is released when the thread or the program ends: an open `FileStream` is closed, an AmigaOS file lock goes** (2026-11-18, #447). Since #446 a jump skips the frames that would have released their locals, so those objects kept `reference_count >= 1`; the exit sweep frees only unmarked objects with a count of 0, and an object only a local held was on no list at all (`first_object` held property-referenced objects only). Their release hooks never ran, and on AmigaOS the file stayed locked after the program had exited. New global feature `releaseHeapOnExit` (`FEATURE_RELEASE_HEAP_ON_EXIT`; `core.h` turns it on by itself for AmigaOS, MorphOS and AROS, whose exit doesn't reclaim files and locks, and `-DAMLC_NO_RELEASE_HEAP_ON_EXIT` turns it off; elsewhere a build target lists it). With it, every object is on its isolate's `first_object` list from allocation to free (linked in the allocators, the fast lanes included, unlinked in `__deallocate_object`; a property count going 0 to 1 no longer links). New `__amlc_release_heap()`, called by `__amlc_isolate_teardown` and by main's generated shutdown (amlc 0.16.0), runs after the statics are dereferenced: the usual mark/sweep (all it does without the feature, with the worker's leak line as before), then, with the feature, the `TRACKOBJECTS` leak report (`Thread 'x' exited with N objects still allocated`, or `Main thread ...`, with up to 20 class names; printed before anything is zeroed, so real ARC leaks after a normal end stay visible), then it sets the code count of every object left to 0 (`reference_count` counts only code's references; property references are `property_reference_count`) and releases them: first those nothing else holds, through the normal ARC death, so a holder's release hook runs before its children go; then the cycles that remain, with every release hook run before any edge is dropped and the memory freed last. Immortal objects are skipped, and so is whatever the statics still reach (the emergency path jumps past their dereference). Natives that hold a code reference: an interface wrapper's reference to its implementation is given back before the release (and no longer counts as a root when marking, so a garbage cycle through one, such as TaskRunner, Thread and its Runnable, is still swept and not reported as a leak); `Continuation`'s release no longer resumes an orphaned suspended frame during this release (`aisolate.releasing_heap`), since that frame's locals are freed by the same pass; the other native releases touch only their own data or property children (`TempFile`, `SslSocketStream`), which the ordering covers. `__mark_root_objects` now also marks every object code still holds (`reference_count > 0`) and follows interface wrappers to their implementation, so the sweep no longer frees what such an object holds by property. Marking is iterative (a work stack on the isolate, recursion only if it can't grow) and deaths during the release are queued rather than recursed into, so a long list held by a skipped frame doesn't overflow the C stack (an AmigaOS task has little). The out-of-memory exception and its message are immortal now (any isolate may throw them). `GC.collect` sees code-held objects as candidates too; they are roots through their count, so what it reclaims is unchanged. Unconditional: the iterative marking and code-held roots, the immortal out-of-memory exception, the `Continuation` guard. Cost, only with the feature: an allocation-heavy loop (two objects and a string per iteration, -O2, linux) takes 0.66 s instead of 0.64 s (about 3%); without it, 0.63 s, as before. Tests: `HeapReleaseTests` (a nested stream in a cycle left open by a worker is closed when it ends and can be read back and deleted; a cycle through an interface; `GC.collect` keeps what a local holds), and `examples/OomShutdown/run.sh` with three new modes (`main-file`, `main-sticky-file`, `worker-file`: a nested stream held by locals, a `FileStream` in a cycle and a 20000-node list, open when the jump comes) plus AddressSanitizer + `TRACKOBJECTS` builds of every mode on linux-x64, with the feature (no use-after-free, no leak, `Allocated objects 2`) and without (no use-after-free; what skipped frames held stays allocated, e.g. `Allocated objects 23` in `main-file`); on AmigaOS under amiberry the files can be deleted after the program exits (with the old core, `Delete` fails with RC 5 and the worker's files can't be read back).

- **A throw or return leaving a `suspend(cont)` body no longer frees the suspend state under the running frame** (2026-11-16, #298). New `Continuation.__claim`, which the compiler calls before that release.
- **Byte is `signed char` in the natives** (2026-11-10, #209). Plain `char` is unsigned on ARM and PowerPC, so `-128B` read back as 128 there.
